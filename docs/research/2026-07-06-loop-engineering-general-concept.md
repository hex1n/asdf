# Loop Engineering 是什么（通用概念解读，不参考本仓库定义）

> 本文刻意脱离本仓库（asdf-skills）里那套具体的"个人工作循环"定义，仅从
> agentic AI / 控制论角度给出概念性解读。**"loop engineering" 不是一个有统一
> 权威定义的行业标准术语**，以下是基于自主代理与反馈控制的解释，非教科书定义。

## 一句话

Loop engineering（循环工程）指：**把"让 AI 代理反复迭代直到达成目标"这件事
本身当作一个可设计、可控制的工程对象去构建**——你设计的不是某一次调用，而是那个
"感知 → 行动 → 观察结果 → 再行动"的闭环：它的驱动、终止、约束、状态和纠错都是
被工程化的部件。重点从"写好一次提示 / 一段代码"转移到"设计好那个会自己转很多圈
的环"。

## 为什么会有这个概念

单次 LLM 调用是无状态的一问一答，能力天花板很低。解决复杂任务（写代码、排查
bug、做研究）靠的是**多轮迭代**：试一下 → 看报错 → 改 → 再试。早期这些循环大多是
隐式、临时的——要么靠人每轮敲"继续"，要么代码里写个 `while` 硬凑。

当循环变复杂，暴露出的共性问题恰恰是经典**控制系统**的问题：

- **驱动**：每一圈由谁来推？人？定时器？还是代理拿着目标自己推？
- **终止**：什么时候算完？靠什么判断？怎么防无限空转或提前收手？
- **反馈信号**：代理靠什么"观察"上一步结果？（测试输出、报错、工具返回）
- **状态管理**：多轮之间怎么保留记忆而不撑爆上下文窗口？
- **约束与安全**：怎么防它中途跑偏、越权、做不可逆的破坏？
- **收敛性**：它在逼近目标，还是原地打转、越改越糟？

Loop engineering 就是把这些从"碰运气"变成"有意设计的工程决策"的那门手艺。

## 一个典型的循环长什么样

```
目标 + 完成判据
      │
      ▼
  ┌─────────────────────────────┐
  │  行动(调工具/写代码/查资料) │
  │        │                    │
  │        ▼                    │
  │  观察结果(测试/报错/输出)   │
  │        │                    │
  │        ▼                    │
  │  判断:达标了吗? ──否──┐    │
  └──────────│───────────┘    │
             是             ↑___│(带着反馈再来一圈)
             ▼
            停,交付
```

工程化就体现在每个箭头上：判据怎么写成机器可查、反馈怎么喂回去、"再来一圈"要不要
清空上下文重开、多少圈没进展就强制停。

## 它和相邻概念的区别

- **Prompt engineering**：优化"一次说什么"。Loop engineering 优化"这个环怎么转、
  何时停"——一层更外面。
- **Agent / agentic AI**：是"能自主循环的系统"这个产物本身。Loop engineering 是
  构建和调校那个循环的**方法与纪律**。
- **Workflow orchestration（工作流编排）**：通常是预先画死的 DAG / 状态机，步骤
  固定。循环工程更强调**开放式迭代**——步数不定，靠反馈和判据动态决定还转不转。
- **控制论 / 反馈控制**：思想母体。"设定值 - 反馈 - 误差 - 调节"换成了
  "目标判据 - 观察 - 未达标 - 再行动"。

## 核心难点（为什么它算"工程"）

真正难的不是"让它转起来"，而是**让它可靠地停在对的地方**：

1. **判停**——最难。判据太松会提前收手，太严或没判据会无限烧钱；还得区分
   "成功停"和"卡住了但停不下来"。
2. **收敛而非震荡**——防止 A 改 B、B 改回 A 来回抖，或每轮都"看起来快好了"其实
   没进展。
3. **上下文经济**——每圈都往上下文塞历史迟早爆；要么摘要，要么每圈重喂干净上下文
   （fresh context）。
4. **越界防护**——自主度越高，一次跑偏的破坏力越大，所以约束要**前置**，不能靠
   事后补救。
