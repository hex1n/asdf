## 建议（当前最佳路径）

在账务/回调处理表上为**支付网关的交易号（或商户订单号）建唯一约束**，并把回调写路径改造成"同一事务内先占位插入、冲突即短路"的幂等模式：占位插入成功才继续执行扣款/记账，插入因唯一冲突失败则直接返回成功 ack、不重复执行扣款逻辑。这是数据库层面强一致、业界对支付回调去重的标准范式，团队现有权限（回调服务+账务表结构）可直接落地，预计 3.5 人天。

## 最佳性检查

| 检查 | 结论 |
|---|---|
| 拟合标准 | ①覆盖至少一次投递的全部重试路径 ②账务强一致(只记一次账且不误杀合法交易) ③交付成本低、用现有权限/技术栈可落地 ④长期维护成本趋近于零 ⑤不阻塞支付链路时延 |
| 胜出方案 | DB 唯一约束 + 同事务占位插入（方案A） |
| 最接近替代方案 | 消息队列削峰+异步处理（方案C）——价值在于降低"处理慢导致超时"的重试频率，但不能替代方案A的去重核心，且新增外部依赖，交付成本更高 |
| 反超条件 | 若团队未来 QPS/时延压力大幅上升，"先ACK再异步处理"从优化项变为必须项时，方案C（或其子机制）价值上升——但那是叠加项，不替代方案A |
| 边际递减停止点 | 一旦"幂等键是否稳定存在"验证通过、事务原子性设计定稿，继续比较其他去重机制不会再改变机制选择或下一步动作，应停止比选、转入验收要素补全 |

## 下一步验证（成本最低、能推翻方案的检查）

**读一份最近一次重复扣款事件的两次回调原始报文，比对其中的网关交易号/商户订单号字段是否跨重试保持一致。** 这是当前推荐机制唯一的翻转条件：如果这个标识不存在或不稳定，唯一约束方案不成立，需要退化为"时间窗+金额+账户"的模糊去重（风险更高、误判概率更大）。主流支付网关几乎都保证这一点，因此按安全默认值先给出方案A，但把这一验证列为落地前第一步，而非事后才发现的阻塞项。

## 验收证据（BUILD 计划的验收标准）

- 用上月11笔真实重复扣款报文在预生产环境重放：第二次回调应命中唯一约束冲突、被短路，账务表中该笔交易只留一条最终记录。
- 边界场景：模拟"占位插入成功但扣款执行失败"，状态机应把该记录标记为可安全重试，避免误杀合法重试导致漏账。
- 上线一周内：幂等冲突命中次数 > 0（证明确实拦截了本会重复的请求），新增重复扣款客诉数为 0。

**发布顺序约束**（非任务拆分）：唯一索引/状态字段的 schema 迁移必须先于写路径改造上线，且用支持在线建索引的方式操作，避免锁表影响支付主链路可用性。

## 根问题与约束拆分（追溯）

根问题：回调处理缺少唯一性去重机制，"至少一次"重试语义下同一笔通知被处理两次；解决 = 无论投递多少次账务只记一次，且不漏记合法独立交易。真实约束：至少一次投递不可消除；财务正确性双向（不重记不漏记）；核心链路安全上线不可长时间锁表。惯例：无防护+事后人工退款是可改历史做法，已被监管预警证明不可持续。

假设审计：①网关标识跨重试稳定唯一（行业惯例默认，读真实报文验证）；②改造权限已确认；③人工拦截不可行是结构性的；④超时来自网络/网关侧而非处理逻辑过慢——若错则"快速ACK"从可选升级为并行高优。
