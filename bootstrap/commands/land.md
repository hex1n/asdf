description: "Landing loop: restate the touch list and completion criterion, then iterate edit→verify→review→fix until the criterion passes. Use after a plan is approved (落地/按方案落地)."
argument-hint: "[方案路径或落地描述；可附完成判据与 Touch 清单]"
---

把命令后的文本（$ARGUMENTS）当作本次落地的输入：方案路径或描述，可能附带完成判据与 Touch 清单。按以下循环契约执行：

1. **落地前复述**：目标仓库/工作目录 + Touch 清单（将改的文件/表/接口）+ 完成判据（测试命令、SQL 断言或预期响应，必须机器可查）。缺判据或缺清单 → 先向用户索要，不动手；微小改动（单文件、无数据/接口影响）可用一句"现状 → 期望"代替正式判据；涉及权限、资金、数据一致性的改动升档——先写可复现的失败测试再动手。对清单中假设存在的表/接口/字段，动手前先用只读工具核验存在性，不凭记忆下结论。
2. **循环执行**：改 → 跑最小相关验证 → 自审 → 修，直到判据满足。非平凡改动的自审开**独立上下文**的只读子代理（不复用执行时的对话历史），只审正确性与需求缺口（不审风格偏好），产出按 P1（必须修）/ P2（应该修）/ P3（可选）分级——仅 P1 中断循环去修，P2/P3 列入结束报告。每轮改完用 git status 核对实际改动是否都在声明的仓库与 Touch 清单内。
3. **中途不询问用户**，除非四种情况：需要触碰 Touch 清单外的文件/表（立即停下确认）；判据被证明不可达（说明证据后停）；连续两轮改动与失败现象均无实质变化（无进展，报告后停）；同一失败重复两次或迭代超过 8 轮（报告卡点后停）。
4. **遵守 Execution Contract**：数据默认保留；行为等价约束；不主动 git 操作；并行推进多个循环时各用独立 git worktree，不共享工作目录。
5. **结束报告**：判据验证结果原文、实际触碰清单与声明清单的 diff、P2/P3 遗留项、遗留风险与后续建议。若因 8 轮/无进展判停：报告必须含**可续跑状态快照**（已改文件、剩余判据、当前失败现象）；若任务本身需要更长跨度，先把 spec/计划/状态落成持久化文档再停，供下一会话续接。若本次属于返工（修复此前已交付的工作），在仓库 docs/rework-log.md 追加一行归因记录（无此文件则先创建）。

> Claude Code 端可用原生 `/goal <完成判据>` 承接本循环的跨轮自动推进，免人工敲"继续"（Codex 端无对应机制，此为单端可选加速项）。
