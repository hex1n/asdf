> 仓库侧依据为 [bootstrap/README.md](../../bootstrap/README.md)、

## 一句话结论

通用概念回答的是"怎么把 agent 的迭代环做成工程对象"；本仓库这套在完整实现了
这件事之外，把问题重新定义成了**"人机混合的个人工作循环"工程**——设计对象不只是
agent 的环，还包括人在环里的位置（撤出三个机械角色、只保留三个判断角色），并且把
"循环本身作为可分发资产"和"循环改进自己的元循环"做成了一等公民。这三点是通用
概念里基本不存在的。

## 相同点：通用概念的每个部件都有对应实现

通用框架的六个工程问题，仓库对每个都有具体落地，且普遍比通用做法更严格：

| 通用概念的部件 | 仓库里的实现 | 超出通用做法的地方 |
|---|---|---|
| **驱动**（谁推每一圈） | 驱动器：`/goal` 每轮复查判据续跑、`ralph-loop` 重喂 fresh context；三条"循环启动语"授权一次 | 明确"驱动器 + 判据闸门 + 判据三者合起来才闭合"，不是单点机制 |
| **终止判据** | 机器可查的 done-when（测试/SQL/diff/schema/阈值五种形态） | **red-at-init**：判据在开工前必须是红的，已绿则拒绝 init——"判据无法区分'做完'和'没开始'就不算判据"（`loop-core/REFERENCE.md`） |
| **判停执行** | Stop hook 判据闸门：判据不绿不放行 `success` | 判停从"agent 自觉"升级为**机器裁决**；且判据要求幂等只读，因为每次 stop 都重跑 |
| **反馈信号** | Evidence 纪律：工具输出/diff/SQL 才算证据，prose 不算 | "事实校验"是硬规则：声称已完成必须指向真实工具结果 |
| **状态管理** | `.agent-loop/` 运行态 + 非成功终态强制"可续跑快照"；fresh context 重喂解决上下文经济 | 快照格式被规定（已改文件/剩余判据/当前失败/下一步） |
| **越界防护** | Run Contract（prose）→ Runtime Contract（machine JSON）→ PreToolUse hook 拦截；git 操作单独授权 | 约束前置做成**双层**：先口头复述，再机器落档拦截 |
| **收敛性** | 同错两次/两轮无进展 → `stalled`；8 轮 → `exhausted`；`amend` 改判据不补预算 | "amend 修目标不买轮次"防住"移动球门柱换取续命"——通用讨论很少想到这层 |

## 差异点

### 1. 设计对象不同——agent 的环 vs 人机混合的环

通用概念的主语是 agent：怎么让**它**转得好、停得对。本仓库的主语是**"每天的实际
工作"**：playbook 开篇即"缺的不是循环，是把人从三个机械角色（人肉时钟/人肉
判停器/人肉守卫）中撤出来"，同时**刻意保留**人的三个判断角色——拍板、部署、验收。
部署被明确标注为"真约束"，不追求自动化掉。这是一个通用文献里没有的人机分工理论：
机械的归机器，判断的归人。

### 2. 有"不循环"的档位

通用概念默认你要转环。本仓库第一步是**判档**：微小改动一句"现状→期望"直接做，
只有显式要求或不可逆/高风险才升到完整循环，且"用户拍板后不再回到收敛"。循环是
**有成本的、按需启用的**，防的是过度流程化——通用讨论几乎是盲区（都在讲怎么建环，
很少讲何时不该建）。

### 3. 循环本身是可分发的产品

通用概念里循环是某个应用的内部结构。本仓库把循环做成**跨机器、跨运行时
（Claude Code + Codex）可安装的资产**：契约卡、hooks、CLI 由 `install.mjs` 幂等
分发，双端同义有 `test_bootstrap_contract_parity.py` 守护，还有
Source / Managed / Cache Drift 一整套分发领域语言。"loop engineering" 在这里既指
用循环干活，也指**维护循环这个产品**。

### 4. 有二阶环（元循环）

通用概念是一阶的：环 → 任务完成。本仓库多了**改进环自己的环**：月度跑 session
语料分析，看四个量化指标（"继续"脉冲词频次、abort 次数、范围漂移纠正占比、开场带
硬判据占比），drift 出的改进候选过 Rule Harvest Gate（重复两次才固化）和证据循环
（baseline → 最窄修改 → 独立证伪）才能进 skill。指标设计里的清醒句："数字不动 =
打法没被采用"——先怀疑采用度，再考虑加机制。

### 5. 终态是五值语义，不是二值

通用概念区分"成功停 / 卡住"。本仓库是五个终态
（`success/noop/blocked/stalled/exhausted`），并明确划分**机器能裁决哪三个**
（success/stalled/exhausted，来自判据 verdict 和计数器）、**哪两个只能 agent 自述**
（noop/blocked，"为什么没事可做"机器推不出来）。"机器持有 vs 代理声明"的边界划分
相当精细。

### 6. 威胁模型收窄是显式决策

通用概念容易含糊"防跑偏"。本仓库白纸黑字写明**判据闸门是协作式兜底，不是对抗性
防线**：防的是无意的提前判停；刻意规避的 agent 可以改 `.agent-loop/` 状态绕过
闸门，防这个需要签名/树外状态，"本仓不做"（`bootstrap/README.md` 边界与威胁模型）。
把"不防什么"写得和"防什么"一样清楚是工程成熟度的标志，但也意味着这套机制的可信
边界依赖 agent 的合作性。

## 小结

| | 通用 loop engineering | 本仓库这套 |
|---|---|---|
| 设计对象 | agent 的迭代环 | 人机混合的个人工作循环 |
| 人的角色 | 常含糊为 "human in the loop" | 精确：撤出 3 个机械角色，保留 3 个判断角色 |
| 循环启用 | 默认转环 | 判档制，默认轻量，不轻易开环 |
| 判停 | 概念上"要可靠停对" | red-at-init + 机器闸门 + 五值终态 + amend 不补预算 |
| 分发 | 不在议题内 | 一等公民（安装器/契约卡/双端同义） |
| 自我改进 | 不在议题内 | 元循环 + 量化 loop-health 指标 |
| 安全边界 | 常含糊 | 显式协作式威胁模型，写明不防刻意绕过 |

总体评价：本仓库这套可视为通用 loop engineering 在"个人生产力系统"这个问题域上的
一个**完整且自洽的实例化**，在人机分工、判停语义、元循环三处走得比通用讨论更远；
代价是显式放弃对抗性防护，可信度以 agent 合作为前提。
