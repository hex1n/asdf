# 支付回调重复扣款 — 最佳方案

**模式**: Plan（"先不写代码，给出最佳方案"）
**深度**: Deep（复发性资金事故 + 监管投诉预警 + 机制选型有非显而易见的权衡）
**输入来源**: 用户请求原文 + 补充上下文（团队规模/权限）。本次为纯文本方案讨论，未读取实际回调服务代码或账务表结构——相关假设已标注 `? unverified`。

---

## 建议（当前最佳路径）

在账务/流水表上为**网关下发的全局唯一业务标识**建立**唯一索引**，回调处理时在**同一本地事务**内先尝试插入一条"该笔交易已处理"的判重记录：插入成功才继续执行扣款，插入因唯一键冲突失败则直接返回网关期望的成功响应、不再执行扣款逻辑。不依赖新增基础设施，三人小组可在现有权限范围内独立完成。

**最佳性检查**：
- 判定标准：①杜绝并发/重试双重扣款（硬性）②改造范围小③不引入新基础设施④不影响扣款性能⑤可观测/可审计（应对监管问询）
- 胜出方案：唯一约束 + 同事务判重（方案 A）
- 最接近替代方案：状态机 + CAS 抢占更新（方案 B），需要区分"处理中/失败重试"细状态时更强
- 何时该换：扣款链路变成跨系统长时间异步等待、需人工介入复核中间态时，B 值得叠加
- 边际收益停止点：确认唯一索引+同事务判重杜绝重复扣款且补齐判重埋点后，继续精修选型收益很小，转向落地与迁移安全

**下一步验证**（决策翻转检查，成本最低、实施前）：
1. 抽取上月 11 笔重复扣款日志时间线，确认是否都对应"同一笔支付被网关多次回调"根因——若存在其他根因案例，那部分需单独定性。
2. 排查账务表历史数据是否已存在与拟建唯一索引冲突的重复记录——若有，需先定"保留哪条"的清理规则（业务侧确认）。

## 问题根因与约束拆分（补充说明）

**根问题**：网关回调 at-least-once 投递语义下，业务处理逻辑没有幂等保护，把"可能重复通知"当"只通知一次"处理。

**真实约束**：①网关 at-least-once、超时重试（外部契约）②团队具备改造权限（给定）③无可靠人工拦截（用户声明）。

**假设（? unverified）**：①回调同步执行到扣款、无状态判断；②判重记录与扣款能否落同一本地事务（若跨外部资金系统，幂等键透传已列为 Core 行）；③11笔是否全部由回调重试触发（下一步验证核心）。

**方案对比与反转测试**：A vs B（状态机+CAS，复杂中间态更强但需超时兜底）、C（分布式锁仅解决并发，重试仍需持久化判重兜底）、D（消息队列消费端去重，本质仍需 A/B 判重逻辑，过度设计）。反转测试：若扣款跨不可合并事务的外部调用，本地判重不够——缓解为幂等键透传（行业标准能力），风险可控。

本次机制选型不构成"选错代价高、难以回退"量级——A 是可平滑叠加 B 的地基性动作，采用同上下文轻量对比，未升级独立锦标赛（用户也未要求独立起草）。

**开放问题**：网关超时窗口与重试策略（影响 Optional"快速200"是否值得）；11笔事故日志根因分布（决定覆盖面）。验证后与假设不符则收窄/调整方案范围，不推翻 BUILD 决策本身。
