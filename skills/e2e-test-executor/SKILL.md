# E2E Test Executor

Execute an existing E2E plan: a real run, a report, and a local issues queue when bugs exist. Write or modify tests only when the user explicitly asks, or when the plan explicitly names authoring test code as the execution method; a scenario's `Automation` level classifies coverage and is never that authorization.

Supported environments: local and test only. If the target is preprod, staging with production-like restrictions, or production, stop and ask for a narrower read-only task or explicit safety instructions.

Output language: use the language the user explicitly requests; otherwise infer from the user's latest prompt, then the plan's dominant language. Write the report and all run artifacts in that language; preserve code identifiers, paths, API names, enum values, logs, and quoted source text as-is. If the language choice remains ambiguous, state the assumed output language once.

Read [REFERENCE.md](REFERENCE.md) before the first trigger; it defines the boundary, scheduling, oracle, and artifact tables.

## Principle

The only product of a run is a **verdict**, and a verdict is trustworthy only when a fault, if present, would pass all four **RIPR** steps and the proof survives. Four invariants follow, and every rule below serves one of them:

- **I1 Controllability** (reach, infect) — the SUT is in the scenario's starting state, triggered through a legitimate channel, isolated from the other scenarios.
- **I2 Observability** (propagate, reveal) — the probe reads the committed outcome the fault would reach, and the oracle has the power to tell right from wrong.
- **I3 Evidence integrity** — proof is captured in **order of volatility**, before anything that could destroy it, and a pass is proven the same way as a failure.
- **I4 Provenance** — plan → run → artifacts → follow-ups is reconstructible from the artifacts alone.

## 1. Intake

Read the plan before touching the system. A plan whose header declares `Contract: e2e-plan/v2` keeps its facts in canonical records rather than pre-built views: read `Scenario Contracts` for mechanics, capabilities, waits, side effects, isolation, and cleanup; `Gates` (`GT-*`) for entry prerequisites, status, and blocking rules; `Gaps` (`G-*`) for unresolved facts and their dispositions; `Coverage Obligations` and `Flow and Impact Edges` for what each scenario must close. Derive the execution DAG and run order from `Depends on`, `Consumes`, `Produces`, `Slice`, and `Priority` — that contract carries no `Execution DAG`, `Execution Order`, or handoff-index section, and a plan holding one is invalid, so never wait for one. For a plan predating that contract, read the equivalent named sections it does carry. If the plan lacks a needed locator, variable, command, table, or environment fact, explore the codebase, docs, config, scripts, tests, and safe read-only probes before asking the user.

Execution starts from a readable plan artifact. When the plan lives only in conversation — a proposal, a design discussion, a fix list — materialize it first: when scenario design is the real ask, including a bare "run E2E tests" with no flow, change, or fix to derive from, hand off to e2e-test-planner (`Plan mode: delta` for a bounded change) and resume from the artifact it produces as `Upstream plan`, once; otherwise write the derived scenario set as `plan-snapshot.md` in the run directory with lineage marked `ad-hoc`, so `Upstream plan` always names a path a fresh agent can re-read. The snapshot holds only scenarios the conversation implies; filling in the execution facts an implied scenario needs — locators, credentials, required intermediate steps found in the sources — is derivation, not invention.

When this run continues a prior run — a re-run to verify fixes — first read the prior run's `execution-report.md`: take its `failed` and `blocked` scenarios plus open defects as the selection set, carry its `Environment State Ledger` as the resume snapshot (what persists, what must not be cleaned), and record it as `Upstream run`, writing this continuation's results as its own run directory that back-links the prior report — a prior report is never edited in place. Re-run those scenarios and their DAG dependents — whatever consumed the fixed behavior — not only the single fixed scenario and not the whole plan, so a fix-induced downstream regression is caught. The deployment fingerprint (§2) must show the fix is the loaded build before re-validating. A previously `failed` scenario that now meets its probes flips to `passed`; update its defect status and back-link the lineage.

On any start or continuation, re-read the user's latest constraints before trusting the plan, and record an `Execution Contract Override` ([REFERENCE.md](REFERENCE.md#execution-contract-override)) for anything the user changed since the plan was written — excluded scenarios, a data-retention decision, tool constraints (e.g. MCP-only, no CLI), or a changed exit criterion. An override **supersedes** the matching plan default: mark that plan requirement `superseded`, never report it as `failed` or unmet.

Completion criterion: every selected scenario is mapped to plan IDs, edge IDs, expected variables, required capabilities, waits, cleanup, and blockers; missing or conflicting plan facts are recorded before execution starts, and `Upstream plan` resolves to a readable artifact path (the materialized snapshot when the plan was conversational). For a re-run, the selection set is the prior run's failed and blocked scenarios plus their dependents, and the upstream run is recorded.

## 2. Controllability (I1)

A scenario is triggered only once three things are pinned: the SUT boundary, the starting state, and its place in the schedule.

### SUT boundary

Declare, before the first trigger, every dependency the selected scenarios reach and whether it is **real** or a **double** (stub, record/replay, fixture), with the double's source and owner — the `SUT Boundary` table in [REFERENCE.md](REFERENCE.md#sut-boundary). A dependency with no declared boundary cannot carry a verdict. When a real dependency — a third-party service, database, message queue, cache, or callback endpoint — is unreachable at run time, switch to its declared double; if none is declared and the scenario needs the live dependency, mark the scenario `blocked` or suspend per the plan's gates, capture the unreachable evidence (endpoint, error, timestamp, retry), and classify it as an `environment defect` — never `passed`, and a `product defect` only when product code actually executed and returned the fault. The one exception is a scenario whose declared purpose and `Automation` level is the dependency-down, timeout, or recovery path: there the outage is an expected input, and the scenario passes only when its expected degraded behavior — fallback, retry, compensation, or error contract — is observed and asserted.

### Trigger channel

Identify whether the run is local or test. Build an `Execution Capability Map` covering available API/RPC/SDK/CLI/UI tools, DB access, MQ/cache/job/callback controls, logs/metrics/traces, auth, base URLs, test accounts, feature flags, service start commands, stubs, build/test toolchains, dependency caches, and cleanup mechanisms. Treat the trigger channel itself as a first-class gate, not just endpoint reachability: the permission, allowlist, routing-override, and fallback-route controls that authorize a trigger on whatever surface applies — for RPC/SDK these are invoke and service allowlists, target overrides, and direct-URL fallbacks; for HTTP, API-key/origin allowlists, gateway routes, and CORS — together with the runtime env that unlocks them; surface these as a named `Trigger Channel Gates` facet of the capability map. Before a real trigger, be able to localize a block to a specific layer such as tool permission, network connectivity, service registration, or business handler rather than reporting a generic failure. When a scenario cannot run for lack of a capability — a tool, an adapter, an MCP surface, a UI selector, or an access right — attribute it as `BLOCKED-BY-TOOLING` naming the specific missing capability, never a generic failure or an `incomplete`.

For any trigger surface, prefer a project-declared execution adapter, test harness, CLI wrapper, browser driver, queue/job tool, callback harness, or other safe command over hand-written mechanics ([REFERENCE.md](REFERENCE.md#execution-adapter-boundary)). This executor owns scenario selection, environment gates, data policy, evidence capture, diagnosis, cleanup, and reporting; the adapter or tool owns surface-specific target or locator resolution, capability discovery, safe describe/dry-run behavior, request or action encoding, metadata/options, invocation, and replay mechanics. A harness or adapter here is an entry that already exists and is invoked as-is — an existing test, script, task, or command; authoring a new test file or test method is writing tests under the intro's authorization rule, not using a harness.

### Starting state

The starting state is three facts pinned together; a scenario whose three are not all pinned does not trigger.

**Environment fingerprint.** For local runs, actively fix reversible environment problems: start declared services, workers, schedulers, stubs, or docker compose; free or change ports; install declared dependencies; create temporary config; run migrations or seeds; and inspect logs until health checks pass or the blocker is proven. The agent's non-interactive shell resolves PATH and the active toolchain differently from a human interactive shell; resolve and record the actual tool paths and versions the run will use before building or starting services. Log every file, command, port, profile, service, toolchain version, cache or dependency source, and temporary change. Classify cache misses, dependency downloads, and dependency-resolution timeouts as environment or tooling setup unless product code actually executed and failed. Do not silently change business logic, bypass auth or validation, or edit production templates to make a scenario pass. For test runs, automatic data creation, cleanup, job triggering, and callback triggering are allowed once the environment is confirmed as test. Then run the `Environment Contract` preflight ([REFERENCE.md](REFERENCE.md#environment-contract-preflight)): resolve and record concrete values, not profile-name inferences or `reachable`, for the effective datasource (and the schema the code expects), the build/run toolchain identity, and the running process's **deployment fingerprint** — a version, build number, commit, start time, or a behavioral fingerprint whose result differs between old and new code. A reachable endpoint is not a fingerprint: a stale process means the fault is never reached, whatever the probe later reads. After any change to config, profiles, feature flags, stubs, service state, seed data, test data, or a redeploy, re-run the readiness probe and verify the next observed response, row, event, log, or artifact reflects the new state; treat cache hits, `unchanged` responses, stale snapshots, reused fixtures, or missing fingerprints as a risk until proven fresh. An unresolved in-scope contract field is a blocker, not an assumption carried into execution.

**Data ownership.** Prefer creating the business data needed for this run through business entry points or existing test tools. Reuse environment data only as a heuristic choice for stable, low-side-effect, normally preconfigured inputs such as accounts, tenants, products, templates, switches, dictionaries, or provider configuration — an open list. When reusing data, record the ID, source, current state, why it was not created, whether the run can mutate it, and how reproducibility or cleanup is affected. Mark data that may be mutated but cannot be restored as blocked or downgrade the scenario to read-only verification. Direct DB mutation is allowed in test environments when it is the practical test hook, but every write/delete is logged with ownership and cleanup evidence. Decide the run's data policy before executing and confirm it rather than letting the user discover it afterward: clean (restore created data to zero) or preserve traces (leave self-owned rows, files, and queue state for later inspection). Default to preserve traces for local/test E2E runs, because repair agents may need the data and scenes for issue-driven fixes and post-fix reruns; clean immediately only when the user explicitly asks for cleanup, the plan requires zero retained data, or the created data is provably irrelevant to debugging and rerun reproducibility. Record the chosen policy — strategy, retention scope, cleanable keys, and items that must not be cleaned — in the `Environment State Ledger`. When the policy is preserve, or the user requires data retention, re-risk every scenario whose plan `Side-effect Classes` include `soft-delete`, `destructive-delete`, `scope-mutation`, `config-change`, or `external-effect`: without explicit authorization, downgrade it to read-only verification using existing evidence or a dedicated new fixture. Failure-recovery and replay paths use a dedicated failure-injection fixture; already-succeeded state stays untouched.

**Schedule.** Build a runtime DAG from the plan; file order is not an order. Decide every pair's placement from the `Scheduling by Root Cause` table in [REFERENCE.md](REFERENCE.md#scheduling-by-root-cause): each row names one way scenarios interfere (order dependency, shared mutable state, asynchronous wait, resource leak, time or randomness, disruptive load) and the decision it forces. Default to serializing: a pair runs in parallel only when its isolation keys differ **and** the records show no shared mutable target — compare `Target locator`, the edge `Effects` and `Readers/receivers` they close, and `External target/stub` for a common route, table, queue, job, flag, cache, or external endpoint; differing isolation keys alone never prove safety, since two run-scoped scenarios can still contend on one global flag, queue, or external quota. When the records leave a pair's overlap unstated, serialize it and say why. Run dependent chains in DAG order and pass produced variables explicitly; run disruptive nodes in isolation; finish with final consistency and cleanup checks across DB, events, logs, metrics, stubs, external side effects, and created data.

Completion criterion: every dependency the selected scenarios reach has a boundary row; the capability map satisfies the entry gates including trigger-channel permissions, or names exact blockers; the Environment Contract preflight holds concrete values; every created or reused entity has an owner marker such as batch ID, prefix, creator, tenant, trace ID, remark, or scenario ID, plus a retention decision, TTL, and cleanup command; the data policy is recorded in the ledger; every parallel, serialized, isolated, skipped, or blocked node cites the root-cause row that placed it.

## 3. Observability (I2)

**Oracle type.** Every verdict names its oracle from the `Oracle Types` table in [REFERENCE.md](REFERENCE.md#oracle-types): `specified` (the plan's concrete expected value), `derived` (a differential, replay, or invariant computed independently of the implementation), or `implicit` (no crash, no error). An `implicit` oracle has no power to reveal a wrong value, so its verdict is at most `unverified`, never `passed`.

**Probe placement.** The probe reads the committed outcome the plan's Expected Results name — the table row, event, external effect, or user-visible state at the end of propagation — not the entry response that accepted the request. A scenario passes only when its expected probes, waits, invariants, side effects, and cleanup evidence are satisfied; a missing probe is blocked, not passed.

**Verdict-evidence parity.** A `passed` verdict is earned by the same class of retained proof as a failure — never by narration alone. Every executed scenario carries four proof items: the exact probe command(s), the raw unsummarized output (response, query result, state dump) verbatim in a fenced block, the created-entity identifiers, and the exact re-query command (SQL, API call, or CLI) an auditor can run against the live datasource to independently spot-check the claim. A verdict whose raw evidence was not retained, or whose re-query no longer reproduces the claimed state, is reported as `unverified`.

**Diagnosis.** Classify every mismatch before filing it: `product defect`, `plan defect`, `environment defect`, `tooling defect`, or `unknown`.

Completion criterion: each selected scenario is `passed`, `failed`, `blocked`, `skipped`, or `unverified`, names its oracle type, and carries its four proof items or an explicit reason they are unavailable, with a diagnosis for every failure or blocker.

## 4. Evidence and Provenance (I3, I4)

### Order of volatility

On any failure, suspected product defect, or unknown mismatch, preserve the failure scene before cleanup: raw request/response, DB rows or query results, queue/job state, logs/traces/metrics, stub or external-system state, config/profile/feature flags, created entity IDs, correlation IDs, screenshots when relevant, and the exact rerun command. Redact secrets while keeping identifiers needed for reproduction. Created data, queues, locks, cache entries, and temporary configs needed for diagnosis stay in place until the scene is captured; if cleanup would destroy evidence, quarantine or retain self-owned data and record owner, TTL, cleanup command, and risk.

### Run artifacts

Create a run directory unless the user specifies an output path; default it beside the plan being executed — under the plan's `docs/e2e-test/<feature>/` folder — so the plan and its runs stay paired, otherwise a stated working path whose full location the final response names. Each entry below exists only on the condition its comment names.

```text
e2e-run-<plan-name>-<timestamp>/
  execution-report.md        # core: single reading path, agent handoff, and inline per-scenario proof
  scripts/                   # core when the run creates data: runnable seed + cleanup scripts
  issues/                    # conditional core: local fix queue for OPEN actionable root causes
    index.md
    ISSUE-001-<short-slug>.md
  attachments/               # conditional overflow: large raw payloads, screenshots, long logs
  # optional, on demand:
  run-metadata.json          # when a programmatic consumer needs machine metadata
  scenario-results.jsonl     # when rerun/comparison tooling consumes per-node rows
  execution-report.html      # when a human stakeholder asks for a rendered report
```

`execution-report.md` is the agent handoff source of truth; its sections, files, and field contracts are in [REFERENCE.md](REFERENCE.md#run-artifact-contract), [Scenario Results & Evidence Legibility](REFERENCE.md#scenario-results--evidence-legibility), [Run Lineage & Emergent Scenarios](REFERENCE.md#run-lineage--emergent-scenarios), and [Environment State Ledger](REFERENCE.md#environment-state-ledger). The rules that decide what goes where:

- The four proof items of every executed scenario sit inline in `Evidence & Failure Scenes`, one proof chain per scenario, so the verdict and its proof share one reading path. Spill an item into `attachments/` only when its raw form is non-textual (screenshot, binary, base64) or so large that inlining it would drown the probe→expected→actual chain — judged by readability, not a line count — leaving a one-line summary, the attachment path, and the re-query command in the report. When one batch probe covered several scenarios, keep its raw output once and point each scenario at its slice.
- A `Scenario Results` row carries status, oracle type, one-line expected and actual, the §3 diagnosis token, an issue link, and one evidence link. The failure reason and disposition live once in `Failures / Defects / Plan Gaps`, keyed by root cause; a defect spanning several scenarios is written once, gets one issue document, and every affected row links to it.
- The ledger's `deployment/freshness evidence` carries the §2 fingerprint. Every emergent out-of-plan finding is a lineage-table row, so no P0/P1 finding is left only in prose.
- When the run creates data, emit runnable seed and cleanup scripts under `scripts/` (idempotent where the surface allows, named so they pair up) and reference them from `Data Created & Cleanup` and the ledger — a prose-only cleanup command does not satisfy this when the run had a scriptable surface.
- Every item in `Failures / Defects / Plan Gaps` carries a **disposition** ([REFERENCE.md](REFERENCE.md#gap--defect-disposition)); every `OPEN` actionable root cause links to an `issues/ISSUE-*.md` document from both that section and each affected `Scenario Results` row. `Next Actions for Agent` lists only `OPEN`, truly-executable steps; a `CONDITIONAL` or `BLOCKED-BY-TOOLING` item stays in Failures/Defects with its precondition or missing capability named.
- `issues/` is a local agent-ready fix queue, one document per actionable root cause with `Issue ID`, `Type`, `Severity`, `Disposition`, `Affected scenarios / edges`, `Expected`, `Actual`, `Evidence / scene`, `Suspected code area`, `Reproduction steps`, `Fix constraints`, `Verification command or scenario`, `Post-fix E2E rerun`, `Closure rule`, and `Cleanup / data impact`. Product defects are fix candidates; plan defects revise the plan; environment and tooling defects repair execution. Remote tracker creation stays out of scope unless explicitly requested.
- Optional artifacts are projections of `execution-report.md` and add no facts: `run-metadata.json` and `scenario-results.jsonl` from `Run Metadata` and `Scenario Results`, `execution-report.html` as a rendering that may add summary cards, filters, and collapsible evidence. Each preserves the report's disposition/status columns, blocking notes, ignored items, and data-retention policy; check a render for escape residue and broken tables so a clean Markdown is never contradicted by it.

### Provenance

Lineage is a **PROV** triple: the *entities* (`Upstream plan`, `Upstream run`, this run's artifacts, `Downstream`), the *activity* (this run — its selection set, overrides, start and end), and the *agents* (the executing runtime and the instruction that triggered it), recorded in `Run Lineage & Emergent Scenarios`; the `Environment State Ledger` is the activity's terminal snapshot. Any rerun or investigation this run spawns back-links to the source plan and the prior run.

### Fix loop

When the user's instruction authorizes iterating until green (for example continue until criteria pass or fix until all pass), treat this run as one iteration of a fix loop rather than a terminal handoff. The report and `issues/` stay unchanged; the final response must additionally name the `OPEN` actionable issues, the exact continuation selection set per §1's re-run rule, and the loop stop condition — no `OPEN` actionable root causes remaining, a blocker only the user can resolve such as a redeploy, or the user's stated cap (default: eight E2E rerun cycles when unstated — this skill's own unit, one full re-run, not a calling-loop round). Fixing product code stays out of this skill's scope: the calling agent drives the loop, dispatching product defects to the repair flow and plan defects to the planner, then triggering each issue's `Post-fix E2E rerun`.

Completion criterion: the final response links or names the report directory, summarizes pass/fail/blocked counts, and calls out whether cleanup completed; `execution-report.md` exists with every scenario's proof chain inline and its lineage triple filled, issue documents exist for every `OPEN` actionable root cause, each issue names its post-fix E2E rerun and closure rule, and optional or overflow artifacts are produced only when a consumer or payload size requires them.
