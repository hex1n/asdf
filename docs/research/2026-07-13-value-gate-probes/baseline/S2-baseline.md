# 支付回调重复扣款 — 幂等防护方案

**模式**：方案（Plan） ｜ **深度**：深度（Deep）—— 高频（日几十次超时重试）+ 重大影响（核心收入链路 + 监管投诉预警）+ 当前无可靠替代
**输入来源**：仅用户请求原文 + 补充上下文（探针环境说明）；本次未读取任何代码/文档（场景本身未提供仓库），涉及支付网关重试行为的表述标注为 `?未验证`（基于行业通行的网关重试语义推断，非本次实测）。

## 建议：当前最佳路径

**根因不是"没抓住重试"，而是回调处理本身不具备幂等性。** 推荐机制：幂等键 + 数据库唯一约束下的原子写入（upsert / 唯一索引冲突捕获），作为主防线；辅以（视根因排查结果）快速 ACK 异步化，以及对账兜底 job 作为安全网。

## 最佳性检查

| 检查项 | 结论 |
|---|---|
| 拟合标准 | ①跨长时间窗口持久防重复 ②数据库层原子性 ③改动范围可控 ④不误伤合法首次通知 ⑤有明确可观测验证指标 |
| 胜出方案 | 幂等键 + 账务表唯一约束 / 原子 upsert |
| 最接近替代 | 快速 ACK + 队列异步去重消费（互补而非替代） |
| 击败条件 | 若证实网关重试严格发生在极短并发窗口内且团队被禁止改动账务表结构 |
| 边际增益止损点 | 再引入分布式事务框架/Saga/独立去重微服务属于过度设计 |
