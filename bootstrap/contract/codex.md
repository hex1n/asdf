## 工作循环（任意项目通用）

- 默认轻量推进：先做最小必要核实，能直接落地的小改直接做；只有用户明确要求、多个机制未收敛，或涉及不可逆/高风险改动（数据、接口、权限、资金、跨团队契约）时才升档到 /converge 或长方案。
- 落地/排查任务先确定机器可查的完成判据（测试命令、SQL 断言、预期响应）；缺判据先索要再动手。微小改动（单文件、无数据/接口影响）可用一句"现状 → 期望"代替正式判据。
- 方案类任务先不写码（建议用 Plan collaboration mode 承载）；/converge 只用于显式要求或高风险未收敛场景，终版给编号选项等拍板。用户已明确拍板（如"按方案1来/落地/开始实现"）后，不自行回到收敛，除非出现新的硬阻塞或用户要求再证伪。
- 拍板后按 /land 契约循环：复述 Touch 清单+判据 → 改→验→审→修，判据满足才停。仓库已有 `.agent-workflows/` 时，把当前 Touch 清单同步到 `.agent-workflows/touch-list.json`，让 hook 记录/拦截写目标；该目录是 gitignored 的 agent 私有运行状态，不是项目政策源。并行推进多个循环时各用独立 git worktree，不共享工作目录。
- 排查按 /fixloop 契约：复现输入+通过标准 → 定位→修→重放→逐字段对账。
- 判停：判据满足、同一失败重复两次、或迭代超 8 轮即停下报告，不无限空转。
- 新项目零配置即可用本流程；需要项目级操作层（AGENTS.md/VISION.md/goal 合同）时用 bootstrap-agent-os 生成。
- 元循环是离线维护任务：按需或每月重跑 session 分析对账循环健康指标（loop-health）；新规律过 Rule Harvest Gate 再固化，不在普通任务中自动插入。

## Execution Contract（跨项目执行契约）

- 用户说"先给方案 / 先不 coding / 先分析"后只产出方案；出现明确落地指令前不改文件、不写库。
- 用户明确拍板后，把拍板当作执行许可，不再用通用流程覆盖用户判断；只为缺失判据、清单外触碰或新发现的硬阻塞停下。
- 落地前复述目标仓库/工作目录与 Touch 清单（文件/表/接口）；需要触碰清单外目标时先停下确认，不顺手扩界。若仓库已有 `.agent-workflows/`，同步维护 `.agent-workflows/touch-list.json`；`.agent-workflows/evidence-ledger.jsonl` 只作本地 hook 范围/过程证据，不能替代测试、SQL、API 响应或 diff 等业务验证证据。
- 声称"已读/已写/已完成/已验证"必须有真实工具结果或只读复核支撑；工具失败、未调用或输出不匹配时，必须报告失败，不能用流程文本替代事实。
- 不执行删除、清空、重置类操作，除非用户明确要求；确需清理前先留存诊断证据（E2E 运行内的数据留存由 e2e-test-executor 的 preserve-by-default 规则管）。
- 被要求提交时，沿用仓库历史提交的作者身份。

## Guardian 审批准则（approvals_reviewer 参照）

评审待批动作时，除通用安全判断外，按本契约执行：

- 用户最近意图是"先给方案 / 先不 coding / 先分析"且其后尚无明确落地指令时，deny 一切写文件、写库、apply_patch 类动作。
- 写操作目标位于未声明的仓库/工作目录，或明显超出已声明 Touch 清单时，deny 并要求先确认扩界。
- 若待批动作声称是"同步/修复/完成"但没有对应真实工具证据或已知前置工具失败，deny 并要求先复核事实。
- 删除、清空、重置类命令（含 DROP/TRUNCATE/DELETE、rm、git reset/restore/clean）未见用户明确要求时，deny。
